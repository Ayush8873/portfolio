01 / about

Making releases boring, on purpose.

I joined SegueIT in January 2026 as a Junior DevOps Engineer and was promoted to DevOps Engineer L2 after probation in August 2026. Day to day I own the release path for a mix of client and in-house applications: GitHub Actions pipelines, Docker images in Amazon ECR and Azure Container Registry, deployments to EC2, Lightsail, Amplify and Azure, and NGINX as the front door.

The work I care about is the unglamorous part that makes production calm: images you can trace back to a commit, servers without long-lived keys, health checks that test the real application, deployments that can't overlap, and monitoring that tells you whether a problem sits in the host, the container or the code. I also handle system administration for the company, manage client AWS accounts through AWS Organizations, and document everything I set up and change.

how I work

  1. traceEvery image is tagged with its Git commit SHA, so any release maps to its source.
  2. least-privEC2 pulls from ECR through a scoped IAM role. One OU per client in AWS Organizations.
  3. verifyDeploys check /health and run smoke tests, rather than trusting container status.
  4. observeMetrics, logs and uptime checks, so incidents get narrowed down quickly.
  5. documentEverything I set up and change gets written down.

02 / workflow

How code reaches production

The delivery pipeline I run across projects. Select a stage to see what happens there and which tools I use.

Source

Changes are pushed to GitHub and deployment workflows trigger from the approved branch. The pharmacy platform lives in a pnpm/Turborepo monorepo with a Next.js storefront and a NestJS API side by side.

  • Git
  • GitHub
  • pnpm / Turborepo

Continuous integration

GitHub Actions runs lint, tests and the monorepo build before anything is packaged. Production deploys run on a self-hosted runner; static sites build on AWS Amplify with branch-based builds. I also built a GitLab CE + GitLab Runner pipeline as a proof of concept.

  • GitHub Actions
  • Self-hosted runners
  • AWS Amplify CI/CD
  • GitLab CI (POC)

Package

Separate Docker images for the API and web app, each tagged with the Git commit SHA so a running container can always be traced back to the exact source it came from.

  • Docker
  • Docker Compose
  • Commit-SHA tags

Registry

AWS workloads push to Amazon ECR; Azure workloads push to Azure Container Registry. EC2 authenticates to ECR through an IAM instance role scoped to the repositories it needs, which removed long-lived access keys from the servers.

  • Amazon ECR
  • Azure Container Registry
  • IAM instance roles

Deploy

Targets vary by project: EC2 with Docker Compose behind NGINX, Azure, AWS Lightsail, AWS Amplify and cPanel-managed servers. Production deploys take a deployment lock so two releases can never overlap, and NGINX config is validated before every reload. The pharmacy platform releases blue/green: the new version is health-checked on the idle stack before NGINX switches traffic, and the previous stack stays ready for rollback.

  • EC2
  • Azure
  • Lightsail
  • Amplify
  • cPanel
  • Deployment lock
  • Blue/green
  • Rollback

Verify

Deploy scripts hit the API and frontend /health endpoints and run smoke tests, and check container state, instead of relying on Docker's status alone. The lock is only released once the release is verified and reported.

  • /health checks
  • Smoke tests
  • Container state

Observe

Node Exporter, cAdvisor and Promtail on the production server feed Prometheus, Loki, Grafana and Alertmanager on a separate monitoring server. Segue Monitor, our white-labelled Uptime Kuma, runs HTTP and keyword checks and posts down/up alerts to a Zoho Cliq channel. CloudWatch covers AWS resources, and I'm adding Zabbix.

  • Prometheus
  • Grafana
  • Loki / Promtail
  • Alertmanager
  • cAdvisor
  • Segue Monitor
  • Zoho Cliq alerts
  • CloudWatch
  • Zabbix (in progress)

Objective
Ship two services from one pnpm/Turborepo monorepo to AWS with repeatable, traceable releases and no manual steps on the server.
Approach
GitHub Actions runs lint, tests and the monorepo build, builds separate API and web images tagged with the commit SHA, and pushes them to ECR. EC2 pulls through an IAM instance role and restarts the stack behind NGINX. RDS PostgreSQL with Prisma migrations, S3 for files delivered through CloudFront, CloudWatch for EC2 and RDS metrics and logs.
Challenges
Knowing a release is really healthy, not just that a container started; keeping AWS keys off the server; separating test and production configuration; config changes that could break NGINX on reload.
Outcome
In production with blue/green releases: the new version is verified on /health for both services and smoke-tested before NGINX switches traffic, and the previous stack stays up for instant rollback. Containers run with restart policies, nginx -t runs before every reload, and every release maps to a commit.

Objective
Keep a production backend serving /v1/ REST APIs and Socket.IO connections reliable, and make problems quick to locate.
Approach
GitHub Actions builds the Docker image and pushes it to ECR; a self-hosted runner on the server takes a deployment lock, deploys to EC2, verifies container state and health, then releases the lock and reports. RDS holds the data and S3 the files. NGINX handles TLS, /v1/ routing, rate limiting (10 req/s with burst) and WebSocket upgrades with timeouts tuned for long-lived connections.
Challenges
Real-time connections dropping behind a proxy; overlapping deployments interfering with each other; telling host, container and application issues apart; keeping monitoring alive when the production server itself is in trouble.
Outcome
In production. Prometheus, Loki, Grafana and Alertmanager run on a separate monitoring server, so the dashboards stay up when production doesn't. Host, container and log telemetry sit in one Grafana view, with alert rules for target down, high CPU, low disk, memory pressure and container restarts.
